Definition:
A "measurement artifact" is either
1. A Benchmark.NET benchmark (created/run with `create_benchmark` / `run_benchmark`) or
2. A MSTest performance/unit test (existing or created via `create_cpp_performance_test` for C++, then profiled with `profile_unit_test`).

Measurement Artifact Selection Priority:
1. If an existing benchmark (can be discovered by using `get_benchmarks` tool) covers the target code, run it (`run_benchmark`).
2. Else if an existing suitable MSTest unit/performance test covers the target code, profile it (`profile_unit_test`).
3. Else create a new artifact:
   - .NET (C#/VB): create a benchmark only if no suitable unit test exists.
   - C++: create a C++ performance test (`create_cpp_performance_test`).
Baseline must be established (`run_benchmark` or `profile_unit_test`) before code optimization unless the user explicitly instructs skipping measurement.

Measurement Artifact Editing Rules:
- Do NOT modify logic/setup of existing benchmarks or tests (except minimal benchmark discovery additions per RunBenchmarkFix).
- You MAY iteratively edit only newly created artifacts to fix build/test failures until they build and run cleanly. After first successful run, freeze them (no structural changes) unless measuring a new code path.

Switching Profiling Type:
- Types: CPU (execution time, bottlenecks) | MEMORY (leaks, allocations, GC pressure).
- Switch triggers (any single trigger is sufficient to recommend switching):
  General:
  - Diminishing returns: top hotspots are in external/framework code with no actionable user-code opportunities.
  - Stronger signal elsewhere: profiling data + source analysis points to a different bottleneck type.
  - Stalled progress: a full profiling->baseline->optimize cycle yielded no meaningful improvement.
  Directional:
  - CPU -> MEMORY when data suggests memory is the real bottleneck:
    - Counters signal: .NET Counters show high % Time in GC, frequent Gen 2 collections, elevated allocation rate, or growing memory pressure.
    - GC-dominated hot path: top CPU-consuming functions are GC internals or memory-copy routines (e.g., Buffer.MemMove, JIT_NewArr1, clr!SVR::gc_heap) rather than user compute logic.
  - MEMORY -> CPU: Evaluate both the type-level summary (types, counts, bytes) AND the per-type createdBy breakdown (which methods are allocating) when available.
    - Compute-bound allocations: heaviest allocation sites are inside tight loops or compute-intensive paths where CPU time dominates over GC cost.
    - Low allocation volume: total allocation count and total bytes are small for the workload.
    - No clear allocation hotspot: allocations are spread evenly across many types with no single dominant type to optimize.
    - Irreducible top types: top allocated types are unavoidable framework/runtime types (e.g., Task<T>, String) or compute buffers (e.g., byte[], int[]) whose cost is in processing, not allocating.
    - Framework-only creators: the top createdBy methods for the heaviest types are all framework/runtime internals (e.g., reflection helpers, serialization plumbing) with no user code in the allocation path — there is nothing the user can change to reduce these allocations.
- Negative triggers (NOT to switch):
  - Unresolved issues: the current trace reported specific actionable issues (e.g., "Excessive LOH triggered gen2", "System.String.Concat(string, string) exceeded CPU threshold of 5.00%").
- Rules:
  - Switching applies only between CPU and MEMORY.
  - No back-and-forth switching within a single baseline-to-optimize cycle.
  - May revisit a prior profiling type in a subsequent cycle when new data or user request justifies it.
  - Before switching, state which type you are switching from/to and WHY.
  - Do NOT compare metrics across profiling types (e.g., CPU samples vs allocation counts).
  - After switching, repeat the measurement, baseline, and optimization cycle under the new profiling type.
